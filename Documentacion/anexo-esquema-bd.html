Gestión del esquema de base de datos: de la maqueta a producción

Cómo Spring Boot crea y evoluciona las tablas, qué queries se disparan cuando cambiás el modelo, qué conviene en producción, y la recomendación concreta para Yerbanalytics como maqueta de tesis.

01 — LA DISTINCIÓN BASE

DDL vs. DML: dos tipos de queries que no son lo mismo

Antes de todo, esta distinción te sirve para siempre. Toda instrucción SQL cae en una de dos familias:

FamiliaQué tocaEjemplos¿Cuándo corre?
DDL
Data Definition Language		La estructura (las tablas y columnas)CREATE TABLE, ALTER TABLE, DROPAl arrancar la app (Hibernate reconcilia el esquema)
DML
Data Manipulation Language		Los datos (las filas)INSERT, UPDATE, DELETE, SELECTEn runtime, cada vez que se ejecuta la lógica

Cuando el motor de reglas guarde un bloqueo o lea sectores, dispara DML en runtime. Cuando modificás una entidad Java, Hibernate dispara DDL al arrancar. Son dos momentos distintos — no los confundas.

02 — LAS DOS ESTRATEGIAS

Cómo se crean las tablas, y los modos de ddl-auto

Hay dos formas de crear el esquema, y son excluyentes: (A) entidades @Entity en Java y Hibernate genera el CREATE TABLE solo, o (B) SQL crudo a mano en schema.sql. Yerbanalytics usa la (A), y su comportamiento lo controla una sola propiedad:

spring.jpa.hibernate.ddl-auto=update

Esa propiedad tiene varios valores posibles, y elegir el correcto es la decisión de fondo:

ValorQué hace al arrancarDónde encaja
noneNo toca el esquema. Vos lo gestionás por fuera.Producción con migraciones
validateVerifica que las tablas coincidan con las entidades. No modifica nada; falla el arranque si no matchean.Producción con migraciones
updateAgrega tablas y columnas nuevas. No borra, no renombra, no cambia tipos.Solo desarrollo
createDropea y recrea TODO el esquema al arrancar (perdés los datos).Tests / dev efímero
create-dropComo create, y además dropea al cerrar la app.Tests

El proyecto está en update: cómodo, cero fricción... pero con una letra chica importante, que es de lo que va la próxima sección.

03 — LA LETRA CHICA

Qué queries se disparan cuando cambiás una entidad

Sí, cambiar una entidad dispara DDL al arrancar. Pero update solo hace cambios aditivos. Mirá los cuatro casos:

✓ Agregás un campo

@Entity @Table(name = "bloqueo_manual")
public class BloqueoManualEntity {
    // ... campos existentes
    private String observaciones;   // ← campo nuevo
}

Al próximo arranque Hibernate corre solo, sin que escribas SQL:

ALTER TABLE bloqueo_manual ADD COLUMN observaciones VARCHAR(255);

✗ Borrás ese campo del Java

Hibernate con update NO corre DROP COLUMN. La columna observaciones queda huérfana en la base para siempre, con sus datos adentro. La app deja de usarla, pero sigue ahí.

✗ Renombrás un campo (observaciones → notas)

Hibernate no entiende que es un rename: crea una columna nueva notas y deja la vieja observaciones con los datos estancados. Terminás con las dos.

✗ Cambiás el tipo (String → Integer)

update normalmente no altera el tipo de una columna existente — es conservador. Podés quedar con un desajuste entre lo que espera Java y lo que hay en la base.

El problema real: schema drift

A esto se le llama deriva del esquema: la base y el código se van separando de a poco, y update no te avisa. En una maqueta que reseteás seguido no duele; en una base con datos reales que no podés perder, es una bomba de tiempo.

04 — PRODUCCIÓN

La mejor práctica: migraciones versionadas

En producción real, el estándar de la industria no es update — son las migraciones versionadas con Flyway o Liquibase. La idea: cada cambio de esquema es un script explícito, numerado, que corre una sola vez y queda registrado.

src/main/resources/db/migration/
  ├── V1__crea_tablas_base.sql
  ├── V2__crea_bloqueo_manual.sql
  └── V3__agrega_columna_observaciones.sql

Flyway lleva una tabla de control (flyway_schema_history) donde anota qué migraciones ya aplicó. Al arrancar, corre solo las que faltan, en orden. Y ahí se combina con ddl-auto=validate: las migraciones crean el esquema, y Hibernate solo verifica que las entidades coincidan.

Criterioddl-auto=updateFlyway / Liquibase
Historial de cambios✗ Ninguno✓ Versionado, en git
Revisable antes de correr✗ No lo ves✓ Es un archivo que revisás en el PR
Borra / renombra / cambia tipos✗ No puede✓ Vos lo escribís, a propósito
Rollback✗ No existe✓ Migración de reversa
Varias instancias arrancando✗ Pueden competir✓ Lock de migración
Esfuerzo de setup✓ Cero~ Requiere escribir scripts

Best practices de gestión de esquema

  • Una sola fuente de verdad. O entidades (dev), o migraciones (prod). Nunca las dos definiendo la misma tabla.
  • Nunca update ni create en producción. Ahí va validate (o none) + migraciones.
  • Cada cambio de esquema = una migración numerada, inmutable una vez mergeada. Si te equivocaste, va una migración nueva, no editás la vieja.
  • Migraciones y datos separados de la lógica de la app, revisadas en el PR como código.
  • Probá la migración contra una copia de datos reales antes de producción, no solo contra una base vacía.
05 — PARA ESTE PROYECTO

Mi recomendación final para Yerbanalytics

Acá está la clave que planteaste vos: esto es una maqueta para tesis, no el producto que van a vender. Eso cambia la respuesta por completo. No apliques best practices de producción por reflejo — aplicá lo que tu contexto necesita.

Recomendación

Dejá ddl-auto=update tal como está. Para una maqueta de tesis es la decisión correcta: cero fricción, la base se recrea y se resiembra con data.sql cuando querés, y no hay datos reales que perder. Meter Flyway ahora sería resolver un problema que no tenés — sobre-ingeniería pura.

Ahora, dos cosas de bajo costo que suben tu nota sin casi esfuerzo, porque demuestran criterio ante el tribunal:

  1. Documentá la decisión. Dejá escrito (en el README del backend o en la defensa) una línea como: "El esquema se gestiona con entidades JPA + ddl-auto=update, apropiado para el alcance de maqueta; una puesta en producción migraría a Flyway con validate." Eso demuestra que sabés la diferencia — que es exactamente lo que un tribunal quiere ver. No saberlo es el problema; elegir update sabiendo, no lo es.
  2. Corregí el design.md del PR #12: sacá la mención a schema.sql y usá el patrón real (BloqueoManualEntity + repository). Coherencia con el resto del código.
En una frase

Para la tesis, ddl-auto=update es la elección pragmática y correcta. La madurez no está en usar Flyway sí o sí — está en saber por qué no lo necesitás todavía y poder explicarlo. Concepto > código.

¿Y si el objetivo de la tesis fuera demostrar arquitectura lista para producción? Ahí sí valdría agregar Flyway con una migración baseline y switchear a validate. Pero eso es una decisión del alcance de la tesis, no una obligación técnica. Definilo vos según qué querés mostrar.
